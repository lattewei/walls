# Claiming an artist wall

Walls are created by producers, not by artists. A wall starts as a **community
page** so anyone can upload a beat for someone they cannot reach. The artist can
later claim that page and take control of how it looks.

Nothing is verified automatically. A human admin reviews every claim.

## Actors

| Actor | Can do |
|-------|--------|
| Anyone | Create a wall, upload a production, report a wall |
| Wall creator | Edit that wall until it is claimed, remove their production |
| Claimant | Submit a claim, publish the code, attach the proof link |
| Claimed owner | Edit the wall (bio, genres, looking for, cover, name) |
| Admin | Review claims, resolve reports, hide tracks |

While a wall is unclaimed or has only pending claims, its creator can edit it.
Once a claim is accepted, the wall belongs to the claimed owner: the creator
loses edit rights, and only the owner or an admin can edit it. The API
computes this per request as `can_edit` on `GET /api/v1/artists/{slug}`.

## States

Page `claim_status`:

- `unclaimed` — community page, nobody has claimed it
- `pending` — at least one claim is waiting for review
- `claimed` — a claim was accepted

Claim `status`:

- `pending` — waiting for admin review
- `accepted` — this claim owns the wall
- `rejected` — denied; the claimant may try again

The public `badge` maps these to UI labels: `community`, `pending_claim`,
`claimed`. Only `claimed` sets `is_official`.

## Flow

1. **Open the claim page.** On a wall, the “Claim this wall” action leads to
   `/artists/{slug}/claim` (login required).
2. **Submit the official account.** The claimant enters the URL of the account
   that speaks for the artist: Instagram, X, TikTok, or the artist’s own site.
   This is `identity_url`, and it is required.
3. **Receive a claim code.** The API creates a `pending` claim and returns a
   short, unique `claim_code` (8 uppercase alphanumerics, generated by the
   database). The page shows it with a copy button.
4. **Publish the code.** The claimant posts the code from the official account —
   a bio line, a story, or a pinned post. This is the actual proof: it shows
   they control the account they submitted.
5. **Attach the post.** The claimant pastes the link to that public post into
   the claim page. `PATCH /api/v1/me/claims/{id}` stores `proof_url` while the
   claim is still pending. They can update or clear it until review.
6. **Admin review.** Admins open `/admin` → Claims. Each row shows the wall, the
   claimant handle, the code, the official account, and the proof post. The
   admin checks that the code really appears on that account, then accepts or
   rejects.
7. **Accepted.** The wall becomes `claimed`, `claimed_by` is set, the owner gets
   `can_edit`, and the wall page shows “Edit wall”.

Rejected claims stay in the claimant’s history. The wall returns to
`unclaimed` unless other claims are still pending, and the claimant can start a
new claim later.

## Rules and edge cases

- **One pending claim per user per wall.** A second request returns
  `409 conflict`.
- **One accepted claim per wall.** Accepting a claim rejects every other pending
  claim for that wall in the same transaction, so nobody is left waiting
  forever.
- **Already claimed.** New claims are rejected with `409 conflict`. The claimant
  should report the wall if the claim is wrong.
- **Claim codes are public.** They are identifiers, not secrets; the admin
  verifies them against the public post. Never treat a code as a password.
- **No email.** Identity is proven through the public account, not an email
  domain.
- **Editing after acceptance.** The owner can change the wall’s name, bio,
  genres, looking-for line, and cover. The URL (`/artists/{slug}`) does not
  change.
- **Creator handover.** Accepting a claim transfers edit control. The original
  creator keeps `can_edit` while the wall is unclaimed or pending, then loses
  it on acceptance. Admins always keep access.
- **Proof is optional at creation.** A claimant can create the claim first, get
  the code, and attach the post later. Admins see “No proof post yet”.

## API

| Endpoint | Auth | Purpose |
|----------|------|---------|
| `POST /api/v1/artists/{slug}/claims` | user | Start a claim with `identity_url` |
| `PATCH /api/v1/me/claims/{id}` | user | Add, update, or clear `proof_url` while pending |
| `GET /api/v1/me/claims` | user | Your claims and their status |
| `GET /api/v1/admin/claims` | admin | Pending claims, oldest first |
| `PATCH /api/v1/admin/claims/{id}` | admin | `accepted` or `rejected` |
| `GET /api/v1/artists/{slug}` | optional | Wall details plus `can_edit` for the caller |
| `PATCH /api/v1/artists/{slug}` | editor | Update wall fields and cover |

Request and response shapes: [api-moderation.md](./api-moderation.md) and
[api-artists.md](./api-artists.md).

## UX notes

- The claim page loads the wall with the session token so the same screen can be
  the claim form, the code/proof step, or an “already claimed” state.
- The wall page fetches `can_edit` client-side because tokens live in
  `localStorage`; server components cannot see them.
- Admins get a “Moderation” link in the sidebar. The link is a convenience only —
  the API checks the current database role on every admin request.
